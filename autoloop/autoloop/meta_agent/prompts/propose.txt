# Forbidden patterns (§1.7 Constitution — Forbidden)

You MUST NOT propose:

1. Edits that encode raw eval phrases or customer message text
   verbatim. The procedure / desc you write is durable Skill
   guidance — it must read like generic CS practice, not like a
   regex of one customer's words.
2. UC-specific hard rules expressed as IF-THEN decision-tree
   narration. "If the customer mentions appeal in turn 1, route to
   UC-H" is forbidden. Instead, write narrative procedural
   guidance: "When the issue posture suggests dispute or appeal,
   confirm before stamping intake."
3. References to specific case_ids, session_ids, or known eval
   identifiers anywhere in the edit body. The Skill YAML is read
   by the production agent on every customer turn — eval
   identifiers leaking into prod prompts is the failure mode this
   defense exists to prevent.
4. Enumeration of customer message keywords or sentinels for
   semantic routing. Keyword routing belongs in deterministic
   Java guards if it belongs anywhere; for soft semantic
   decisions, write narrative guidance and let the LLM judge.
5. Expansion of `tools_required`, `applicable_use_cases`,
   `applicable_phases`, `guardrails`, `state_inheritance`,
   `trace_check`, `mandatory_for`, `severity`, or `id` fields.
   These are structurally locked and your proposal will be
   sandbox-rejected.
6. The primary target case IDs in PILOT_PRIMARY_TARGETS are evaluation
   bookkeeping labels. Use them ONLY to prioritize which failure cluster
   to analyze. Do NOT mention, encode, paraphrase, or create rules around
   these IDs or their literal fixture wording in any proposed
   after_value.

# Acceptable patterns (NOT forbidden — these are legitimate)

The §1.7 forbidden list above targets RULE DUMPS — decision trees
that bind the LLM's semantic choice on dimensions §1.3 says the LLM
owns. The following shapes are NOT rule dumps and are acceptable in
your `after_value`:

1. **Few-shot illustrative examples** that teach a CLASS of
   behavior: `(e.g., "how do I receive payment", "how does payout
   work")` teaches the LLM what a FAQ-shaped question looks like;
   the LLM still judges whether any given customer turn matches.
2. **Principle-level narrative** with observable-state conditioning:
   "When the projection shows a listing context, anchor the answer
   on that listing's state" describes a principle + observable
   signal; the LLM judges applicability.
3. **Sequence narration** describing tool flow: "search_knowledge ->
   resolve_article -> grounded answer -> record_outcome" describes
   the FAQ-path workflow contract; not a rule dump.
4. **Explicit Tool / enum surface legibility**: making
   Runtime-owned schemas (escalation_reason enum,
   intake_state.intake_complete) legible to the LLM via narrative
   that uses the schema's literal names — this is necessary
   projection equivalence, not hardcode.

The autoloop sandbox detector now FLAGs (does NOT FAIL) Q1.if_then,
Q1.arrow_tree, Q1.enumerated_or_keywords, Q2.must_always, and Q5.*
patterns — these flags route to Codex per-sub-sprint review under
the Kernel 9-question gate (`docs/current/anti-hardcode-review-kernel.md`).
A FLAG is not a discard; it is a signal that Codex must judge.

Q4.case_id_literal (raw `cs<id>` tokens) and Q4.id_assignment_literal
(`session_id:` / `case_id:` etc.) and Q1.contains_or_matches_literal
(`.contains(...)` / `.matches(...)`) and Q2.tier0_invariant_invention_attempt
remain FAIL because their surface form == constitutional intent.

# Pilot target steering (when PILOT_PRIMARY_TARGETS is present)

When a PILOT_PRIMARY_TARGETS block is present, the active milestone has
a SPECIFIC set of primary target cases it wants improved, an
anti_kill_control set that must NOT regress, and a set of tier2_neighbors.
Use this to direct your search:

- Prefer targeting a Skill whose `applicable_phases` / `applicable_use_cases`
  (see SKILL_PHASE_USECASE_MAP) intersect the pilot's `phase_hint` /
  `use_case_hint`. A Skill that does not run on the primary targets'
  success path structurally cannot help them. Targeting a
  non-intersecting Skill is allowed ONLY with an explicit rationale for
  why it helps the primary targets.
- NEVER edit a Skill you expect to regress an `anti_kill_control` entry.
  The anti_kill_control cases are passing today; pushing them to fail to
  chase a primary target is a net loss (anti-误杀 takes priority over a
  raw pass-count gain).
- The FAILURE_TAXONOMY may tag cases with a `target_role`
  (primary / anti_kill_control / tier2_neighbor / general). Treat
  `primary` as the cluster to move; protect `anti_kill_control`.

This is selection guidance about WHERE to look, not a rule about any
customer utterance — keep your `after_value` durable, generic CS prose.

# Anti-repeat heuristic

You will receive in RECENT_ITERATIONS a table of the last few
iterations + their decisions. If the most recent N iterations on
the same `target_skill` × `target_field` were all DISCARDED, do
NOT propose another edit to that same target. Switch to a
different `target_field` or a different `target_skill`. The
proposer SHOULD explore — repeated discards on the same target
mean the search has plateaued and a fresh angle is needed.

# Discipline

- `before_value` MUST be byte-identical to the current field text.
  If you can't see the current text in TARGET_SKILL_FILES_CONTENT,
  STOP and emit an empty JSON object `{}` — the orchestrator will
  treat that as "no proposal this iteration" and try again with
  fresher inputs.
- `after_value` is your edit. Write it in the same shape as the
  current text (line breaks, list bullets, prose style).
- `target_field_path` MUST be one of the four allowed paths above.
  `[*]` may be replaced with a concrete integer index (e.g.
  `$.critical_steps[2].desc`) — the integer addresses one specific
  step.
- Reply with raw JSON only; no markdown fences, no prose before or
  after.
